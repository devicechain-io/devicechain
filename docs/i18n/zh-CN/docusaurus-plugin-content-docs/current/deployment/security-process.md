# 安全流程 {#security-process}

本页说明 DeviceChain 如何处理漏洞报告、如何履行欧盟《网络弹性法案》的报告义务、每个版本发布哪些内容，以及如何让协助维护项目的 AI 代理无法接触任何可能发布被篡改构建的环节。本页只描述目前已有的做法，以及尚未具备的部分。

## 报告漏洞 {#reporting}

请始终私下报告，切勿使用公开 issue。报告渠道和受支持的版本见 [SECURITY.md](https://github.com/devicechain-io/devicechain/blob/main/SECURITY.md)。机器可读的联系方式发布在 [`/.well-known/security.txt`](https://docs.devicechain.io/.well-known/security.txt)。

| 步骤 | 目标 |
| --- | --- |
| 确认并初步分级：阅读、复现或驳回，并给出首次严重程度判断 | 24 小时内，每天均如此 |
| 完整评估：是否有效、严重程度、受影响版本 | 7 天内 |
| 按严重程度修复 | 严重 14 天，高 30 天，中 90 天，低则在下一个版本 |

这些是小团队的目标，而非保证。如果某一项无法达成，会向报告者说明原因。

## 《网络弹性法案》下的报告义务 {#cra}

自 2026-09-11 起，制造商必须向主管机构报告其产品中**正在被积极利用**的漏洞，以及影响产品安全的**严重事件**。二者遵循相同的三个步骤，从项目知悉之时起算：

| 步骤 | 被积极利用的漏洞 | 严重事件 |
| --- | --- | --- |
| 预警 | 24 小时内 | 24 小时内 |
| 通报（附当前已知信息） | 72 小时内 | 72 小时内 |
| 最终报告 | 纠正或缓解措施可用后 14 天 | 通报后 1 个月；若届时事件仍在持续，则届时提交进展报告，并在事件处理完毕后 1 个月内提交最终报告 |

维护者遵循的流程：

1. **判断计时是否已经开始。** 积极利用是指有可信证据表明有人未经所有者许可，对真实系统利用了该弱点。研究人员提交的概念验证不会触发计时；有实际攻击的报告则会。
2. **发送预警**，通过欧盟网络安全机构运营的单一报告平台，由其转交相关成员国的国家协调机构（CSIRT）。预警说明这是一份预警、是否怀疑存在恶意行为，以及产品可用的成员国。
3. **72 小时内发送通报**：漏洞性质、受影响版本、已有的缓解措施，以及严重程度评估。
4. **不得无故拖延地告知用户**，在预警发出后、修复出现之前：哪些内容受影响，以及用户现在即可采取的缓解措施（GitHub 安全公告草稿、发布说明或仓库公告）。
5. **发布修复。** 修复后的补丁版本与已公开的 GitHub 安全公告（适用时附 CVE）同时发布，公告会说明升级前需要做的事（如有）。
6. **发送最终报告**，包括根本原因、修复、已知的恶意行为者，以及如何通知用户。
7. **记录**私有公告中每一步的日期，使下一次事件有可参照的实例。

DeviceChain 是不出售的开源软件，因此具体部署是否使其运营者在这些规定下成为制造商，应由该运营者自行判断。无论如何，项目对其发布的软件执行此流程。

## 每个版本发布什么 {#release-artifacts}

每个版本都为每个镜像附带已签名的 SBOM 和构建来源证明（[验证版本](verifying-releases.md)）。当某个公告影响到一个依赖时，维护者会在版本 SBOM 中查找受影响的包和版本，列出暴露的镜像，并随公告发布 OpenVEX 格式的声明：携带该包的镜像为**受影响**或**已修复**，包含该包但无法触及漏洞代码的镜像为**不受影响**并附明确理由。

检查由仓库中的脚本 `hack/vex-exposure.sh` 完成。它读取每个镜像的 SPDX SBOM 和一份公告，列出暴露的镜像并起草声明。没有任何包的 SBOM 会被视为错误，绝不会被当作“没有暴露”。

## 可复现构建 {#reproducible}

对同一个提交在不同机器和不同目录中构建两次，得到逐字节相同的输出，即为**可复现**的构建。CI 中有一个任务，从提交的两份独立解压副本、使用各自独立的缓存构建 `dcctl` 和边缘代理，若摘要不同则失败。该任务通过一个被植入的不确定性构建来验证，它必须能够将其检出。容器镜像和 Helm chart 尚未纳入该任务；broker 镜像有其自己的可复现性检查。

## AI 辅助开发 {#ai-assisted-sdl}

AI 代理为本项目起草代码、文档和评审。它们被视为一个键盘速度异常快的不受信任的贡献者，控制措施并不依赖代理表现良好：

- **没有机密。** 代理运行时无法访问签名身份、镜像仓库凭据或云密钥。发布工作流使用绑定到仓库的短期身份签名，不存在长期签名密钥。
- **没有发布权限。** 代理无法创建标签或发布制品。发布工作流只会从维护者创建的标签运行。
- **不能合并到受保护分支。** 代理只能提交 pull request。必需的检查通过后由维护者合并，与其他任何贡献者相同。
- **不受信任的输入就是数据。** 代理读取的 issue 文本、pull request 描述、公告报告、网页和依赖文档都被当作待分析的数据，绝不当作要遵循的指令。声称“忽略你的规则”的报告本身就是一项发现。
- **评审。** 代理编写的变更由维护者评审，高风险区域还需第二位独立评审者；新的防护检查在被信任之前，必须先证明它能在被植入的缺陷上失败。

## 尚未具备 {#roadmap}

- 容器镜像和 Helm chart 的可复现性检查。
- 将性能测试所用的剩余长期云凭据，替换为来自 CI 的短期工作负载身份访问。
- 针对 OpenSSF Scorecard 和 OpenSSF 基线控制项公布目标分数。Scorecard 已每周运行，结果公开。
