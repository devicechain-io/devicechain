# 长期支持策略 {#long-term-support-policy}

DeviceChain **同一时间指定一条发布线**作为长期支持（LTS）线。LTS 线自指定之日起 **18 个月**内，只以补丁版本的形式接收**安全修复和关键修复**。本页说明这一承诺的含义、修复如何进入该线，以及如何离开该线。它是[版本与升级策略](./versioning-policy.md)的补充，后者仍适用于每个发布，无论是否为 LTS。

**目前尚未指定任何 LTS 线。**指定之后，本页会写明是哪一条线，仓库中也会用一处声明记录它，供发布和回移（backport）工具读取。在此之前，每个发布都遵循通常的[版本模型](./releases-and-upgrades.md#versioning-model)。

## LTS 线接收什么 {#what-it-receives}

| 接收 | 不接收 |
| --- | --- |
| 安全漏洞的修复。 | 新功能、新字段或新操作。 |
| 关键缺陷的修复：数据丢失或损坏、平台无法启动或无法升级、认证或租户隔离失效。 | 性能优化、重构，以及本身不属于安全修复的依赖升级。 |
| 从该线自己的分支打标签的补丁版本（`1.4.1`、`1.4.2`）。 | 新的次版本。新的次版本会在主分支上开启一条新线。 |

只有当引入某项修复的变更带有 `security` 或 `critical` 标签时，该修复才会被提议回移到 LTS 线。其他内容一律不提议，提议也绝不会被自动合并。

## 修复如何进入该线 {#how-fixes-arrive}

LTS 线 `X.Y` 位于名为 `release-X.Y-lts` 的分支上，从 `vX.Y.0` 标签切出。

1. 修复先合入主分支。只存在于 LTS 分支上的修复不被接受。
2. 若带有 `security` 或 `critical` 标签，机器人会开启一个拉取请求，将其 cherry-pick 到 LTS 分支。若提交无法干净地应用，机器人会在原拉取请求上说明，由维护者手动回移。
3. 该拉取请求会针对 LTS 分支运行完整的 CI 矩阵（包括升级演练），并由维护者像对待其他变更一样审查并合并。
4. 该线的补丁版本从 LTS 分支打标签。发布流水线会拒绝从其他位置切出的、属于已建分支之线的补丁标签，因此补丁绝不会夹带主分支上的无关变更。
5. 较旧线的补丁版本绝不会把镜像的 `latest` 标签或 npm 的 `latest` 标签向后移动。其 npm 包会发布在专属标签下，例如 `lts-1-4`。

## 离开该线 {#moving-off}

处于 LTS 线的运维人员不必逐个次版本升级。受支持的升级路径是跳过中间次版本的直接升级：所有被跳过的次版本的全部迁移，会在一次 `dcctl upgrade` 中按顺序执行。在推荐更新的线之前，会先演练这一过程：在 LTS 版本上为实例写入每种实体各一个，直接升级到候选版本，然后读回每一行并确认未变。随后，同一演练会在一个故意植入迁移缺陷的代码树上再运行一次，并且它必须失败；从未见过失败的通过不是证据。

跳过版本之前，请阅读所跳过各版本的升级说明，因为在被跳过的次版本中宣布的弃用，会写在该版本的说明里。

## 本页不作的承诺 {#out-of-scope}

- 同一时间只支持一条 LTS 线。发布说明会宣布何时指定新线，以及上一条线的支持截止日期。
- 不作超过 18 个月的承诺，也没有经 FIPS 验证的构建。
- 安全修复指对 DeviceChain 本身及其随附组件的修复。与其并行运行的其他服务中的漏洞不在本页范围内。
