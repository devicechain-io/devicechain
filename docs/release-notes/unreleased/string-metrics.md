## en

- **A metric can have the data type `STRING`.** A device can report a state or a mode as text, for example `"heating"`, under a metric declared `STRING` on its profile. Declare it in the console's metric form, through the API or with `dcctl`. The reading is stored with the device's history, kept as its last-known value (`textValue` on `latestMeasurements` and on the event queries), and shown in the console's readings list. It is never averaged, summed or charted as a number: an aggregate over it is refused, and a detection rule does not see it as a number, even when the text looks like one (`"12"`). A rule that names a `STRING` metric never fires, and the console's rule authoring and the AI rule drafter do not offer one. A value is at most 4,096 bytes of valid UTF-8 with no NUL byte; a longer or invalid value is dropped on its own, counted as `declared_not_storable`, and shown on the device's page like any other dropped reading, and the rest of the message is kept. Text for a key the profile does not declare is still dropped. A `STRING` metric cannot have a formula. The analytics view of measurements does not expose the text column yet.
- **A device's latest reading can hold text.** The latest-reading projection that `latestMeasurements` serves gains a nullable `textValue` field beside `value`: a reading of a STRING metric keeps its text there and leaves `value` null, and a numeric reading is unchanged. The device page shows the text. Every reading stored before the upgrade keeps its `value` and has a null `textValue`. The change adds one nullable column to the device-state store, with no backfill and no default.
- **A dashboard sample can carry a text reading.** `MeasurementSample` in `@devicechain/dashboards` gains an optional `textValue`, and the live measurement stream now selects it, so a reading from a `STRING` metric reaches a widget as text instead of an unexplained empty value. It is absent on a numeric reading and on a server that predates `STRING` metrics. The built-in widgets still plot and aggregate numbers only and skip a sample whose `value` is null, so a text reading is never drawn as a gap or a zero.
- **`get_latest_measurements` and `query_measurements` return a `STRING` metric's text.** Until now an assistant reading a device's latest values or history saw a `STRING` metric as an empty value. The text now comes back as `text` under the result's `untrusted` member, marked as device-reported, so an assistant treats it as data and never as instructions. A numeric reading is unchanged, and an empty text arrives as no text.
- **The rule editor warns when a rule names a `STRING` metric.** A detection rule never reads a text reading, so a rule that names a metric declared `STRING` on its profile can never fire. The console's rule form now says so while the rule is being written, naming the metric; the rule is still accepted and saved. The check is also available to API clients: `validateDetectionRules` takes an optional `metrics` list (each entry a `key` and a `dataType`, at most 1,000) and answers a `namesStringMetric` warning for each such metric a rule names. Leave the list out and no such warning is given. An unknown `dataType`, or a key listed twice with different types, is refused. The console sends the list only for a profile that has a `STRING` metric, so during a rolling upgrade an older event-processing pod simply gives no inline check for such a profile until the upgrade finishes.

## es

- **Una métrica puede tener el tipo de dato `STRING`.** Un dispositivo puede notificar un estado o un modo como texto, por ejemplo `"heating"`, bajo una métrica declarada `STRING` en su perfil. Se declara en el formulario de métricas de la consola, mediante la API o con `dcctl`. La lectura se guarda en el historial del dispositivo, se conserva como su último valor conocido (`textValue` en `latestMeasurements` y en las consultas de eventos) y aparece en la lista de lecturas de la consola. Nunca se promedia, se suma ni se grafica como número: un agregado sobre ella se rechaza, y una regla de detección no la ve como un número, ni siquiera cuando el texto lo parece (`"12"`). Una regla que nombre una métrica `STRING` nunca se dispara, y la creación de reglas de la consola y el asistente de IA no la ofrecen. Un valor ocupa como máximo 4.096 bytes de UTF-8 válido sin bytes NUL; un valor más largo o no válido se descarta por sí solo, se cuenta como `declared_not_storable` y aparece en la página del dispositivo como cualquier otra lectura descartada, y el resto del mensaje se conserva. El texto de una clave que el perfil no declara se sigue descartando. Una métrica `STRING` no puede tener fórmula. La vista analítica de las mediciones todavía no expone la columna de texto.
- **La última lectura de un dispositivo puede contener texto.** La proyección de última lectura que sirve `latestMeasurements` incorpora un campo `textValue`, que admite nulos, junto a `value`: una lectura de una métrica STRING guarda ahí su texto y deja `value` en nulo, y una lectura numérica no cambia. La página del dispositivo muestra el texto. Toda lectura guardada antes de la actualización conserva su `value` y tiene un `textValue` nulo. El cambio añade una columna que admite nulos al almacén de device-state, sin relleno de datos ni valor por defecto.
- **Una muestra de panel puede llevar una lectura de texto.** `MeasurementSample` en `@devicechain/dashboards` incorpora un `textValue` opcional, y el flujo de mediciones en vivo ahora lo selecciona, de modo que una lectura de una métrica `STRING` llega al widget como texto en lugar de un valor vacío sin explicación. Está ausente en una lectura numérica y en un servidor anterior a las métricas `STRING`. Los widgets integrados siguen graficando y agregando solo números y omiten una muestra cuyo `value` es nulo, así que una lectura de texto nunca se dibuja como un hueco ni como un cero.
- **`get_latest_measurements` y `query_measurements` devuelven el texto de una métrica `STRING`.** Hasta ahora, un asistente que leía los últimos valores o el historial de un dispositivo veía una métrica `STRING` como un valor vacío. Ahora el texto se devuelve como `text` dentro del miembro `untrusted` del resultado, marcado como notificado por el dispositivo, de modo que el asistente lo trata como datos y nunca como instrucciones. Una lectura numérica no cambia, y un texto vacío llega como ausencia de texto.
- **El editor de reglas avisa cuando una regla nombra una métrica `STRING`.** Una regla de detección nunca lee una lectura de texto, así que una regla que nombra una métrica declarada `STRING` en su perfil no puede dispararse. El formulario de reglas de la consola ahora lo indica mientras se escribe la regla, con el nombre de la métrica; la regla se sigue aceptando y guardando. La comprobación también está disponible para los clientes de la API: `validateDetectionRules` admite una lista opcional `metrics` (cada entrada con `key` y `dataType`, como máximo 1.000) y responde con una advertencia `namesStringMetric` por cada una de esas métricas que nombre una regla. Si se omite la lista, no se emite esa advertencia. Un `dataType` desconocido, o una clave repetida con tipos distintos, se rechaza. La consola envía la lista solo para un perfil que tenga una métrica `STRING`, así que durante una actualización progresiva un pod antiguo de event-processing simplemente no ofrece la comprobación en línea para ese perfil hasta que la actualización termine.

## zh-CN

- **指标可以使用 `STRING` 数据类型。** 设备可以把状态或模式作为文本上报（例如 `"heating"`），前提是其配置文件中该指标已声明为 `STRING`。可在控制台的指标表单中、通过 API 或使用 `dcctl` 声明。该读数会与设备的历史一起存储，并作为其最近已知值保留（`latestMeasurements` 和事件查询中的 `textValue`），还会显示在控制台的读数列表中。它绝不会被求平均、求和或按数字绘图：对它做聚合会被拒绝，检测规则也不会把它当作数字，即使文本看起来像数字（`"12"`）。引用 `STRING` 指标的规则永远不会触发，控制台的规则编写和 AI 规则草拟也不会提供它。值最多 4,096 字节，必须是有效的 UTF-8 且不含 NUL 字节；过长或无效的值会被单独丢弃，计入 `declared_not_storable`，并像其他被丢弃的读数一样显示在设备页面上，消息的其余部分会保留。配置文件未声明的键所带的文本仍会被丢弃。`STRING` 指标不能带公式。测量值的分析视图暂未提供文本列。
- **设备的最新读数可以是文本。** `latestMeasurements` 所返回的最新读数投影在 `value` 旁新增了可为空的 `textValue` 字段：STRING 指标的读数把文本保存在其中，并将 `value` 置为 null，数值读数保持不变。设备页面会显示该文本。升级前存储的所有读数仍保留其 `value`，`textValue` 为 null。此变更为 device-state 存储新增一个可为空的列，不回填数据，也没有默认值。
- **仪表板样本可以携带文本读数。** `@devicechain/dashboards` 中的 `MeasurementSample` 新增可选的 `textValue`，实时测量流现在会选取它，因此 `STRING` 指标的读数会作为文本到达小组件，而不是一个无法解释的空值。数值读数以及早于 `STRING` 指标的服务器上不会有该字段。内置小组件仍然只绘制和聚合数字，并会跳过 `value` 为空的样本，因此文本读数绝不会被画成缺口或零。
- **`get_latest_measurements` 和 `query_measurements` 会返回 `STRING` 指标的文本。** 此前，助手读取设备最新值或历史时会把 `STRING` 指标看作空值。现在文本会作为 `text` 返回在结果的 `untrusted` 成员下，并标记为设备上报，因此助手会把它当作数据，而不是指令。数值读数保持不变，空文本则表现为没有文本。
- **规则编辑器会在规则引用 `STRING` 指标时给出警告。** 检测规则从不读取文本读数，因此引用了在其配置文件中声明为 `STRING` 的指标的规则永远不会触发。控制台的规则表单现在会在编写规则时指出这一点并给出指标名称；规则仍会被接受并保存。API 客户端也可使用此检查：`validateDetectionRules` 接受可选的 `metrics` 列表（每项包含 `key` 和 `dataType`，最多 1,000 项），并为规则引用的每个此类指标返回一条 `namesStringMetric` 警告。省略该列表则不会给出此类警告。未知的 `dataType`，或同一键以不同类型重复列出，会被拒绝。控制台仅在配置文件含有 `STRING` 指标时才发送该列表，因此在滚动升级期间，旧版 event-processing Pod 只是暂时不为此类配置文件提供行内检查，直到升级完成。
