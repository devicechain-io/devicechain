# 证书身份 {#device-certificates}

设备可以用**客户端证书**而不是令牌或密码来证明自己的身份。它在 MQTT 连接的 TLS 握手中出示证书，平台检查该证书是否由租户信任的证书颁发机构（CA）签发。固件里不需要烧录任何共享机密，也没有任何东西可以被人从网络上复制一条消息后重放：私钥从不离开设备。

本页说明平台如何决定信任一张证书，以及这种信任到哪里为止。要进行设置，请按[使用证书连接设备](../guides/device-x509.md)操作；控制台一侧见 [预配置与信任锚](../user-guide/provisioning-and-trust-anchors.md)。要运维消息代理并进行监控，见[证书认证](../deployment/device-certificates.md)。

:::note 状态
在**平台消息代理上的 MQTT** 中可用。HTTP 和 LwM2M 不接受客户端证书，C# SDK 只能用 RSA 和 ECDSA 密钥出示客户端证书，证书的自动续期也尚未提供。[不支持的内容](#not-supported)列出了所有未覆盖的部分。
:::

## 信任锚是身份的边界 {#trust-anchor}

**信任锚（trust anchor）**是租户添加的一张 CA 证书，意思是“持有该 CA 所签发证书的设备都是我的设备”。它是公开材料，按原样保存。每个租户最多可以有 32 个。

- 根 CA 或中间 CA 都可以作为信任锚。请锚定在只签发你自己设备的最窄的 CA 上。如果制造商为许多客户运营同一套 PKI，请信任签发你设备群的子 CA，而不是根 CA。
- 每次连接都会重新对照信任锚检查。证书的任何内容都不会被缓存为“已信任”。
- 信任锚可以被禁用。这会立即撤销该 CA，并结束所有依赖它的设备的现有会话。

由于信任锚决定谁是该租户的设备，**不遵循名称约束（name constraints）**。带有名称约束的 CA，在作为信任锚添加时，或出现在设备出示的证书链中时，都会被拒绝。DeviceChain 使用的身份是证书的通用名称（common name），而名称约束并不覆盖它。本来用于限制 CA 可签发范围的约束会被悄悄忽略，所以平台选择拒绝该证书，而不是让你误以为它生效了。

## 证书必须满足什么 {#certificate-rules}

只有同时满足以下全部条件，平台才接受设备证书：

- 在扩展密钥用途中声明了**客户端认证**。没有扩展密钥用途，或允许任意用途的证书会被拒绝：它从未声称自己是客户端证书。
- 它本身不是 CA。
- 它以及它之上的任何证书都没有使用 SHA-1 签名。
- 证书链中的每个密钥都是 2,048 至 8,192 位的 RSA、P-256 或 P-384 的 ECDSA，或 Ed25519。
- 它的证书链（从叶子证书到设备发送的中间证书）能够构建到信任锚。设备最多发送五张证书，总共不超过 16 KiB。
- 当前有效。最多提前五分钟签发的证书也会被接受，以容忍时钟比 CA 略慢的设备；其到期时间绝不会被延长。

## 证书成为设备的两种方式 {#two-ways}

| 方式 | 你要做什么 | 设备的身份 |
| --- | --- | --- |
| **固定凭据（pinned credential）** | 先创建设备，再添加一个 `X509_CERTIFICATE` 凭据，写入它的证书并指明信任锚。 | 你创建的那台设备。令牌由你选择。 |
| **首次连接时注册** | 创建**证书配置（certificate profile）**：一个指明信任锚的自动注册配置。证书链到该信任锚的设备在首次连接时自行注册。 | 为该证书创建的设备。外部 ID 是证书的通用名称，令牌由它派生。 |

**固定凭据**由证书的 SHA-256 标识，由服务器计算。凭据记录证书必须链到的信任锚，以及整条证书链上最早的到期时间。一台设备最多可同时持有三个证书凭据，因此可以在旧证书到期前先加入替换者。已禁用和已过期的凭据在删除之前也计入这三个。

**证书配置**没有需要保管或轮换的注册密文，因为证书本身就是证明。它使用与[自注册](../guides/device-self-registration.md)相同的控制手段：策略、设备数量上限、到期时间，以及撤销它所注册的设备。每个租户最多可以有八个证书配置。

### 派生令牌与客户端 ID {#derived-token}

MQTT 会话以客户端 ID 为键，平台要求客户端 ID 为 `{instanceId}:{tenant}:{deviceToken}`，这样一台设备就无法接管另一台设备的会话。首次连接时注册的设备还没有令牌，所以平台需要一个仅凭证书就能算出的令牌，并且在写入任何数据之前完成计算。由证书注册的设备，其令牌为：

```text
pv-{slug}-{hash}
```

- `slug` 是通用名称中除字母、数字、`-` 和 `_` 之外的每个字符都替换为 `-`，并去掉首尾的 `-` 和 `_`。
- `hash` 是通用名称的 SHA-256 的前 12 个十六进制字符。
- 整个令牌最长 128 个字符；过长的 `slug` 会被截短以适应，截短后留在末尾的 `-` 或 `_` 会被去掉。
- 如果通用名称中没有任何字符能保留进 `slug`，令牌就是 `pv-{hash}`。

因此设备固件可以根据自己的证书算出自己的客户端 ID。[指南](../guides/device-x509.md#client-id)中有一个完整示例。客户端 ID 不匹配的连接会在创建任何内容之前被拒绝，所以被拒绝的连接绝不会留下半成品设备。

事先创建并预指定给某个证书配置的设备必须使用这个令牌。令牌留空时，控制台和 API 会自动填入，填入不同的值则被拒绝。

### 由哪个配置注册设备 {#narrowest-anchor}

一张证书可能链到多个配置的信任锚。其信任锚**离证书最近**的配置胜出，因此锚定在中间 CA 的配置优先于锚定在其根 CA 的配置。如果两个可用配置距离相同，连接会被拒绝而不是随意猜测，并触发告警 `DeviceX509JitMisconfigured`。请给每个配置各自的信任锚，或把其中一个锚定在更窄的 CA 上。

首次连接时注册在策略 `ALLOW_NEW` 下**创建**设备。在 `ALLOW_NEW` 下，该信任锚的 CA 签发的、通用名称尚无设备使用过的任何证书，都会注册一台新设备，直到达到配置的 `maxDevices`。如果这样过于开放，请锚定在最窄的中间 CA 上、设置上限，并在发生泄露时禁用信任锚。采用（adopt）你事先创建并预指定的设备，以及为已持有证书的设备接受续期后的新证书，目前都尚未提供。

## 会话持续多久 {#session-lifetime}

会话的有效期到设备证书、每张中间证书和信任锚（以及凭据自己的到期时间，如果有）三者中最早的 `notAfter` 为止。消息代理在那一刻关闭会话。续期了证书的设备用新证书重新连接。

## 撤销 {#revocation}

| 你需要 | 做法 | 生效时间 |
| --- | --- | --- |
| 停用一台设备 | 禁用或删除它的 `X509_CERTIFICATE` 凭据，或禁用该设备 | 立即；打开的会话被结束 |
| 停用整个 CA | 禁用信任锚 | 立即；所有依赖它的设备的会话被结束 |
| 停用某一张证书（叶证书或中间证书，无论是否已注册） | 用 `revokeDeviceCertificate` 按指纹撤销 | 从该证书下一次连接起，所有副本都生效；它所影响的打开的会话被结束 |
| 停用 CA 已吊销的证书 | 把该 CA 的吊销列表（CRL）上传到信任锚 | 从列表所列每张证书的下一次连接起；列表新列出的证书所对应的打开的会话被结束 |
| 停用自行注册的设备 | `revokeProvisionedDevices` 或 `resetDeviceProvisioning`，与任何[自注册设备](../guides/device-self-registration.md#compromise)相同 | 立即 |
| 让证书自然失效 | 签发短期证书 | 恰好在证书到期时 |

**撤销会在证书连接时拒绝它，并结束它所影响的打开的会话。** 撤销一张叶证书（手动，或由列出它的 CRL），会结束持有它的设备的会话。撤销证书颁发机构的范围更广：当你给出它的证书，或 CRL 列出了某个已注册凭据的证书链曾使用的中间证书时，该信任锚下所有带证书凭据的设备的会话都会被结束，证书链仍受信任的设备会立即重新连接。对一个没有任何已注册凭据被发现使用过的中间证书按裸指纹手动撤销，会拒绝经由它的连接（仅限该信任锚），但不会结束任何会话，因为不知道有什么依赖它。在从早期版本升级的实例上，升级前注册的凭据没有记录中间证书，因此这样的撤销无法判断它影响哪些会话：结果会显示 `sessionsEnded: false`，用该中间证书本身（`certificatePem`）重复撤销，会结束该信任锚下所有设备的会话。会话在撤销提交时结束，10 到 40 秒后再结束一次（第二次在 10 秒后到期，由下一轮每 30 秒运行一次的重试执行），以捕获撤销那一刻正在接入的设备。如果负责结束会话的服务无法确认，撤销仍然有效；结果会显示 `sessionsEnded: false`，重复调用会再次请求。见[升级说明](https://github.com/devicechain-io/devicechain/blob/v1.2.0/docs/docs/deployment/releases-and-upgrades.md#v120-x509-sessions)。

**CRL 只能上传，从不获取。** 平台不会跟随 CRL 分发点。（询问 OCSP 响应方是另一项可选检查，见下文。）你用 `putDeviceRevocationList` 把 CA 的当前列表上传到信任锚（通过 GraphQL 最大 2 MiB），或使用 `device-management` API 上的流式 `PUT /trust-anchors/{token}/crl`，格式为 DER 或 PEM。默认情况下，两种方式的上限均为 2 MiB；只有将 `deviceManagement.callout.revocation.maxCrlBytes` 调高后（最高 32 MiB），流式上传才接受更大的列表。平台会对照信任锚（或你随列表一并发送的签发者链）校验列表的签名，并为每个签发者保留一份当前列表。CRL 编号不高于此前为该签发者接受的所有编号的列表会被拒绝，所以旧列表永远不能替换新列表，即使该列表曾被删除也一样。`deleteDeviceRevocationList` 会删除一份列表及其带来的拒绝。

**手动撤销是平台自己的决定。** `revokeDeviceCertificate` 通过证书的 PEM 或 SHA-256 指纹指定证书，并可附带原因。只要该证书出现在已验证的路径上就会生效，无论其凭据或设备之后如何，所以删除凭据并不能让该证书重新注册。`unrevokeDeviceCertificate` 可将其移除。持有手动撤销的信任锚在撤销被移除之前无法删除。

**信任锚有多严格。** 信任锚有一个撤销模式。`ENTRIES`（默认）拒绝已存列表或手动撤销所列的证书，放行其余证书，无论列表多旧，所以没有列表的信任锚与撤销功能出现之前的行为一致。`REQUIRE_CURRENT` 还会拒绝其签发者没有当前列表的证书；列表在其 `nextUpdate` 加上信任锚的宽限期（`revocationStaleGrace`，最长 168 小时）之前都算作当前。当信任锚没有任何当前列表，或某张已注册证书由没有列表的 CA 签发时，平台会拒绝把它切换到 `REQUIRE_CURRENT`，因为这会拒绝所有这类设备。请关注每份列表的 `status`（`FRESH`、`EXPIRING`、`STALE`），并在它过期之前上传下一份。

**OCSP 是可选的第二道检查，按信任锚配置，默认关闭。** 信任锚有一个 OCSP 模式：`OFF`（默认：不询问任何响应方，也不发送任何请求）、`ENFORCE_KNOWN` 或 `REQUIRE_CURRENT`。在实例开关 `deviceManagement.callout.ocsp.enabled`（默认关闭）打开之前不会询问任何内容；`REQUIRE_CURRENT` 还需要 `allowRequireCurrent`（默认关闭），并且信任锚上要有 `ocspResponderUrl`。开关关闭时，API 会拒绝把信任锚切换到检查模式。若之后开关被关闭，`ENFORCE_KNOWN` 的信任锚按 `OFF` 运行，`REQUIRE_CURRENT` 的信任锚则拒绝新的连接，因为该模式从不放行它无法确认的证书。

该检查在证书链、有效期、列表和手动撤销检查之后运行，所以已被拒绝的证书不会产生任何请求；它会询问信任锚之下每条已验证路径上的每张证书。在两种检查模式下，`revoked` 响应都会拒绝该连接。`unknown` 响应、格式错误或无法验证的响应，以及无法访问、过慢或繁忙的响应方，都算作没有响应，其含义由模式决定：`ENFORCE_KNOWN` 放行该连接并计数（`x509_ocsp_unavailable_allowed_total`），而 `REQUIRE_CURRENT` 会拒绝状态无法确认为当前有效的证书。只有良好的响应才会被缓存，且只缓存有限的时间。

响应方 URL 来自证书的 Authority Information Access 条目，或来自信任锚自己的 `ocspResponderUrl`；后者由租户通过 `updateDeviceTrustAnchor` 设置，并替代证书中的条目。所有查询都经过平台的出站 egress 防护。取自证书的 URL 不适用运营方的允许列表；只有信任锚自己的 `ocspResponderUrl` 才能到达运营方已允许的目标。

当前限制：`revoked` 响应会拒绝该次连接，但目前还不会结束已打开的会话，也不会写入吊销存储，因此除了该次拒绝之外，不会共享给其他证书或副本。没有后台刷新；响应在连接需要时才获取。请仅在滚动升级完成之后才把信任锚切换到检查模式，因为尚未升级的副本不检查 OCSP，可能放行另一个副本拒绝的证书。OCSP 造成的拒绝在 `callout_x509_total` 中计为 `ocsp_revoked`（响应为已撤销）或 `ocsp_unavailable`（`REQUIRE_CURRENT` 无法确认）。

由列表或手动撤销造成的拒绝在 `callout_x509_total` 中计为 `cert_revoked`，由 `REQUIRE_CURRENT` 造成的计为 `revocation_unknown`。短期证书仍然是成本最低的撤销方式；对于等不及到期的证书，才使用吊销列表和手动撤销。

## 不支持的内容 {#not-supported}

- **名称约束。** 带名称约束的 CA 会被拒绝，如上所述。
- **自行获取 CRL，以及会结束会话的 OCSP。** 吊销列表是上传到信任锚的；平台从不获取列表。连接时的 OCSP 检查已存在，按信任锚配置且默认关闭，但已撤销的响应目前还不会结束已打开的会话或更新吊销存储，也没有后台刷新。见[撤销](#revocation)。
- **自动续期，以及在重置注册后重新采用设备。** 已持有一张证书的设备再出示另一张不同的证书时，在连接注册时会被拒绝（`ALREADY_PROVISIONED`）。在续期功能推出之前，请在旧证书到期前把新证书添加为固定凭据（一台设备可持有三个）。
- **C# SDK 中的 Ed25519 密钥。** SDK 可以出示客户端证书，但 .NET 没有 Ed25519，因此无法出示使用该密钥类型的证书。
- **HTTP 摄取与 LwM2M。** 两者都不使用客户端证书认证。HTTP 设备使用令牌或基本凭据，LwM2M 设备使用预共享密钥。在 MQTT 上，如果用户名不是 `{tenant}:@x509`，出示的证书会被忽略，连接仍按其令牌或密码判断，与以前一样。
- **其他消息代理。** 只有平台自己的消息代理支持证书认证。通过运维方自有外部消息代理连接的设备不在覆盖范围内。
- **由平台签发的证书。** CA 和证书都由你自己提供。
