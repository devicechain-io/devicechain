## en

- **The `Instance` resource is now also served as `core.devicechain.io/v1` (preview).** `dcctl install` applies a CRD that serves `v1` beside `v1beta1` with an identical schema, and the stored form is still `v1beta1`, so no object is rewritten and nothing needs converting. `dcctl` and the operator keep reading and writing `v1beta1`, and existing manifests keep applying unchanged. What does change is discovery: Kubernetes prefers the newer version, so an unqualified `kubectl get dci`, and any generic client that asks the API server for the preferred version, now speaks `v1`. Output that prints the `apiVersion` (for example `kubectl get dci -o yaml`) shows `core.devicechain.io/v1`. Only `Instance` gains `v1`: the group's other kinds (`InstanceOperation`, `ExecutorEnrollment`, `InstanceConfiguration`) are still served only as `v1beta1`, so a tool that applies the group's preferred version to every kind in it must ask per kind. Pin a version with `kubectl get instances.v1beta1.core.devicechain.io` if a script depends on the old one. Both versions stay structurally identical for as long as both are served: a field is added to both or to neither.

## es

- **El recurso `Instance` ahora también se sirve como `core.devicechain.io/v1` (versión preliminar).** `dcctl install` aplica un CRD que sirve `v1` junto a `v1beta1` con un esquema idéntico, y la forma almacenada sigue siendo `v1beta1`, por lo que no se reescribe ningún objeto y no hay nada que convertir. `dcctl` y el operador siguen leyendo y escribiendo `v1beta1`, y los manifiestos existentes se siguen aplicando sin cambios. Lo que sí cambia es el descubrimiento: Kubernetes prefiere la versión más nueva, así que un `kubectl get dci` sin calificar, y cualquier cliente genérico que pida al servidor de API la versión preferida, ahora habla `v1`. La salida que imprime el `apiVersion` (por ejemplo `kubectl get dci -o yaml`) muestra `core.devicechain.io/v1`. Solo `Instance` gana `v1`: los demás tipos del grupo (`InstanceOperation`, `ExecutorEnrollment`, `InstanceConfiguration`) siguen sirviéndose solo como `v1beta1`, por lo que una herramienta que aplique la versión preferida del grupo a todos sus tipos debe consultarla por tipo. Fije una versión con `kubectl get instances.v1beta1.core.devicechain.io` si un script depende de la anterior. Ambas versiones se mantienen estructuralmente idénticas mientras se sirvan las dos: un campo se añade a ambas o a ninguna.

## zh-CN

- **`Instance` 资源现在也以 `core.devicechain.io/v1`（预览版）提供服务。** `dcctl install` 应用的 CRD 在 `v1beta1` 之外同时提供 `v1`，两者的 schema 完全相同，存储形式仍为 `v1beta1`，因此不会重写任何对象，也无需转换。`dcctl` 和 operator 继续读写 `v1beta1`，现有清单照常应用。发生变化的是资源发现：Kubernetes 优先选择较新的版本，因此不带版本限定的 `kubectl get dci`，以及任何向 API 服务器请求首选版本的通用客户端，现在使用的是 `v1`。输出中会打印 `apiVersion` 的命令（例如 `kubectl get dci -o yaml`）将显示 `core.devicechain.io/v1`。只有 `Instance` 新增了 `v1`：该组的其他类型（`InstanceOperation`、`ExecutorEnrollment`、`InstanceConfiguration`）仍然只以 `v1beta1` 提供，因此把该组的首选版本套用到组内所有类型的工具必须按类型分别查询。如果脚本依赖旧版本，请使用 `kubectl get instances.v1beta1.core.devicechain.io` 固定版本。只要两个版本同时提供服务，它们在结构上就保持一致：新增字段要么同时加入两者，要么都不加。
