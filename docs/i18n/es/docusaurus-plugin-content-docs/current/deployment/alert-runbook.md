# Guía de alertas

Cada alerta que incluye el chart tiene un `runbook_url` que lleva a su entrada aquí. Cada entrada indica la gravedad de la alerta, qué le está diciendo y qué hacer al respecto. El texto es la propia descripción de la alerta, de modo que la notificación y esta página nunca se contradicen.

Las alertas solo llegan a una persona cuando Alertmanager tiene un receptor. Consulte [Enrutar las alertas a una persona](./observability.md#alert-routing) para configurarlo con `dcctl install --alert-webhook`, `--alert-email` o `--alert-config`.

## `devicechain.area-availability`

### InstanceAreaUnavailable {#instanceareaunavailable}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.area-availability`

an area of this instance has no pod available

**Qué significa y qué hacer.** Deployment ‹deployment› wants ‹value› pod(s) and has had none available for ten minutes, so that area is not serving. Because its pods are gone, the area also stops reporting its own readiness and metrics, and the instance overview's readiness and scrape panels will not show it: this alert and the panel for areas with no pod available are what do. Describe the deployment and its pods: kubectl describe deployment and kubectl get pods in the instance's namespace show a failing image pull, a pod that cannot be scheduled for want of CPU or memory, a failed readiness probe, or a crash before ready (kubectl logs --previous). If the area was scaled to zero by mistake, scale it back; an area you turned off on purpose has zero wanted pods and does not raise this.

## `devicechain.broker`

### BrokerCertificateExpiringSoon {#brokercertificateexpiringsoon}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.broker`

the broker's TLS certificate expires within 30 days

**Qué significa y qué hacer.** The broker server named by the pod label presents a TLS certificate that expires in less than 30 days. When it expires the broker refuses TLS connections from devices and from this instance's own services. The certificate is renewed by dcctl upgrade, which re-issues it inside its last 30 days and swaps it in without restarting the broker when only the certificate changed, so running dcctl upgrade for this instance now clears this alert. If this keeps firing after an upgrade, the broker has not picked the new certificate up; check the server's log, and restart the server pod if it did not switch.

### BrokerCertificateExpiryCritical {#brokercertificateexpirycritical}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.broker`

the broker's TLS certificate expires within 7 days, or already has

**Qué significa y qué hacer.** The broker server named by the pod label presents a TLS certificate that expires in less than 7 days, or that has already expired. Once it has expired the broker's TLS connections fail for devices and for this instance's own services. Run dcctl upgrade for this instance now: it re-issues the certificate under the authority the instance keeps. An instance that does not keep its authority (one bootstrapped by an early release) cannot re-issue it in place and has to be rebuilt; dcctl upgrade says so when that is the case. If an upgrade has run and this still fires, the broker has not picked the new certificate up; restart the server pod.

### BrokerLeadershipImbalanced {#brokerleadershipimbalanced}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.broker`

one broker server leads far fewer streams than the others

**Qué significa y qué hacer.** At least one broker server leads fewer than half the streams an even share would give it, so the others carry the replication and acknowledgement work for it. Only the streams that dcctl is allowed to move are counted: this instance's replicated streams other than the device-ingest ones (the broker's MQTT streams, the device capture stream and every stream an ingest area writes), which are never rebalanced because a leader change on them can lose messages already acknowledged to a device. After a rolling restart of the broker the server restarted last leads nothing, and at the load this was measured under that doubled publish acknowledgement latency and cost a few percent of HTTP ingest. dcctl upgrade evens leadership out after it rolls the broker, so this fires after a restart done any other way (a node drain, a pod loss, a manual rollout), or when that step was skipped or warned. Run dcctl broker rebalance &lt;instance&gt; to even it out; each move is a brief election for one stream. If it keeps returning, check the broker pods for repeated restarts.

### BrokerMqttClientAuthLost {#brokermqttclientauthlost}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.broker`

the broker is not requesting device client certificates

**Qué significa y qué hacer.** The broker server named by the pod label is not asking MQTT devices for a client certificate, so devices that authenticate by certificate cannot connect. Devices that use a token or a password are not affected. Either the server is running but its MQTT listener stopped requesting certificates (a configuration reload that did not keep the setting, or the broker's own check of its listener keeps failing; its log says which), or the server is not running the DeviceChain broker image, for example after a rollback to the upstream nats image. Check the server's image with kubectl get pod -o jsonpath='\{.spec.containers[0].image\}'. On the DeviceChain image, restart the server pod, and report the log lines around the last configuration reload. On the upstream image, certificate devices stay refused until the DeviceChain image is restored.

## `devicechain.command-delivery`

### CommandBatchReserveRefusals {#commandbatchreserverefusals}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.command-delivery`

The delivery-machinery reserve is refusing fleet writes the tenant's ceiling would have admitted

**Qué significa y qué hacer.** Fleet writes are being refused that WOULD have fitted against the tenant's own undelivered-command ceiling, and were refused only by the headroom the delivery machinery reserves for itself. This is the reserve doing its job — nothing is broken and every caller was told — but a rate sustained for this long means the ceiling and the reserve disagree about what a normal fleet write is. Raise the offending tenant's ceiling, or lower the reserve, deliberately. These counters carry NO tenant label — by design, since a tenant is unbounded cardinality — so the Command Delivery dashboard can tell you which codes and which bound, never which tenant. To find the tenant, read the recorded command batches: one that fanned out partially records a per-device HELD_CEILING_EXCEEDED refusal, and a batch refused whole records nothing at all, so a tenant seen here may have left no batch behind.

### CommandClaimsStranded {#commandclaimsstranded}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.command-delivery`

Commands are stranded in SENT and may time out against innocent devices

**Qué significa y qué hacer.** At least one command was left reading SENT after both its publish and its release failed. It was never delivered. What happens next depends on the device's transport, and only one of the two answers is safe. On LwM2M the stranded reconciler re-arms it within about ten minutes, so it is delivered when the device next wakes — check devicechain_commanddelivery_command_delivery_stranded_recovered_total\{disposition="PARKED"\} to confirm that happened. A disposition of CANCELLED there means the opposite: the command's batch had been called off, so the row was cleaned up rather than delivered. On MQTT nothing retries it and it expires as TIMEOUT, which records the failure against the DEVICE. So treat every MQTT TIMEOUT reported in this window as unattributed until this is resolved, and do not send engineers to inspect the devices named. Look for a broker outage overlapping a database outage: it takes BOTH to strand a claim, which is why this counter is normally flat at zero.

### CommandPresenceReadErrors {#commandpresencereaderrors}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.command-delivery`

The command presence gate is failing open

**Qué significa y qué hacer.** The dispatch sweep cannot read the presence projection, and the gate fails OPEN by design — so commands are being dispatched WITHOUT the absence check, to devices nobody confirmed were there. Nothing else reports this: dispatch looks healthy and the holds-placed counter goes to zero, which reads as "no devices are absent" rather than "nothing is being checked". Check the device-state area and the presence projection's own health.

## `devicechain.container-restarts`

### InstanceContainerRestarted {#instancecontainerrestarted}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.container-restarts`

a container in this instance was restarted

**Qué significa y qué hacer.** Kubernetes restarted the container named by the pod and container labels in the last 15 minutes. A DeviceChain service exits on purpose when it cannot do its job, and the reason is in the log of the container that exited: run kubectl logs --previous on the pod and read the last error line, usually after 'A component has declared this process unfit to continue'. A read loop that failed for two minutes with no answer from the message broker names its stream and its last error there. Several services restarting together point at the broker: check that its servers are running and run dcctl ha verify. If the restarted container is a broker server (dc-nats-*), read its previous log too; its streams take a few minutes to be current again. A container whose last state is OOMKilled needs a higher memory limit. Restarts in the first minutes of an install or upgrade are expected. Messages the container had read from the broker but not acknowledged are delivered again, but requests a device or client had in flight to it fail and must be retried, and every restart lengthens the outage it happened in.

## `devicechain.database-backup`

### BackupDestinationAlmostFull {#backupdestinationalmostfull}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

The backup destination is almost full

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is over 85% full. When it fills, WAL archiving starts failing — and failed archiving does not stall commits, it accumulates WAL on the DATABASES' volumes until those fill and PostgreSQL stops. So this ends as a database outage whose cause points nowhere near a database. Grow the volume first. Otherwise remove archives left behind by instances that no longer exist, move to an external destination, or shorten a store's recovery window in the OpenTofu configuration (backup_retention_tsdb for an instance's event store, backup_retention_rdb for the relational store).

### BackupDestinationFillingFast {#backupdestinationfillingfast}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

The backup destination will be full within the hour at its current rate

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is more than 65% full and filling fast enough to run out of space within the hour. When it is full, WAL archiving fails for EVERY database archiving into it, and each primary keeps its unshipped WAL on its own volume until that fills and PostgreSQL stops. Likely causes, in order: an instance ingesting faster than the store was sized for; archives left in the store by instances that no longer exist (list the bucket and compare with the instances that are running); a scheduled base backup that stopped, so nothing is being pruned. Grow the volume, remove what no running instance owns, or move backups to an object store you run yourself.

### PostgresHasNeverArchivedWAL {#postgreshasneverarchivedwal}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

PostgreSQL has never successfully archived a WAL segment

**Qué significa y qué hacer.** ‹pod› has archived no WAL segment, ever. The first base backup forces a segment switch, so a working cluster leaves this state within minutes of creation — an hour in it means archiving has never worked here, not that the database is quiet. Note this records no FAILURE either, so the failing-archival alert cannot see it: an archiver that hangs rather than errors looks exactly like this.

### PostgresNoRecentBaseBackup {#postgresnorecentbasebackup}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.database-backup`

N

**Qué significa y qué hacer.** ‹pod› has taken no successful base backup N. WAL archiving alone restores NOTHING — a recovery replays WAL forward from a base backup, so an ever-growing archive with no recent base is a longer and longer replay onto older and older state. Retention pruning has stopped too: obsolete backups are deleted only after a new backup completes.

### PostgresWALArchiveBacklog {#postgreswalarchivebacklog}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

PostgreSQL is holding WAL it has not shipped to the backup destination

**Qué significa y qué hacer.** ‹pod› has ‹value› WAL segments (16 MiB each) waiting to be archived. They stay on this database's own volume until they ship — the replicas do not help, because a standby does not keep the primary's unshipped WAL — and when the volume fills, PostgreSQL stops and does not fail over. If the WAL archiving failing alert is also firing, the destination is refusing writes: check that the object store is reachable and has space. If it is not, the archiver is slow or hung, or ingest is producing WAL faster than it ships: check the backup sidecar's logs and the object store's free space, and grow the database volume if the backlog keeps rising.

### PostgresWALArchivingFailing {#postgreswalarchivingfailing}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

PostgreSQL WAL archiving is failing

**Qué significa y qué hacer.** ‹pod› last FAILED to archive a WAL segment more recently than it last succeeded, so this database is no longer being backed up. Nothing will stall and nothing will crash: writes continue and every health check stays green. Two things are accumulating — the recovery gap, and unshipped WAL on the database's own volume, which will eventually fill it and stop PostgreSQL. Check the object store is reachable, has space, and still accepts these credentials.

### PostgresWALArchivingNotConfigured {#postgreswalarchivingnotconfigured}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-backup`

A PostgreSQL cluster has no WAL archiver attached and is NOT being backed up

**Qué significa y qué hacer.** ‹pod› is running with archiving switched on and NO backup plugin behind it, so every WAL segment is being "archived" by a command that discards it and reports success. Nothing else will tell you: archived_count rises, no failure is ever recorded, disk does not grow, and every other backup alert stays green. This database cannot be restored to any point in time. Check that the Cluster still carries its barman-cloud entry under spec.plugins and that its ObjectStore exists.

## `devicechain.database-control-plane`

### CNPGClusterNotReady {#cnpgclusternotready}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-control-plane`

A PostgreSQL Cluster has not been Ready for 15 minutes

**Qué significa y qué hacer.** ‹cluster› in namespace ‹namespace› reports Ready=False (‹reason›). THIS BLOCKS FAILOVER: while a Cluster is not reconciling it is never promoted, so losing the primary leaves healthy, fully caught-up replicas that nothing will elect — the databases look fine right up until the moment they need to move. A phase of "Cluster cannot proceed to reconciliation" points at the CloudNativePG operator or the Barman Cloud plugin rather than at Postgres, and the instance pods will look perfectly healthy throughout.

### CNPGClusterStateUnobserved {#cnpgclusterstateunobserved}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.database-control-plane`

No CloudNativePG Cluster conditions are being collected

**Qué significa y qué hacer.** Nothing is reporting PostgreSQL Cluster conditions in namespace ‹namespace›, so the health of database failover is UNKNOWN rather than good — and while this fires, CNPGClusterNotReady CANNOT fire, because it reads the series this rule says are missing. Check, in order: kube-state-metrics is running; it was started with --custom-resource-state-config-file (OpenTofu's monitoring module sets this from cnpg_cluster_metrics, which the root derives from enable_cnpg); and its ClusterRole can list postgresql.cnpg.io/clusters. A missing RBAC rule shows up only as a `forbidden` line in the kube-state-metrics log and an endpoint that exports nothing.

### CNPGClusterUnusable {#cnpgclusterunusable}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-control-plane`

A PostgreSQL instance is not answering its own metrics collector

**Qué significa y qué hacer.** At least one instance of ‹cluster› in namespace ‹namespace› cannot be queried by its CloudNativePG metrics collector, while the pods and the Cluster's Ready condition may look perfectly healthy — the operator holds reserved superuser connections, so it keeps reconciling either way. This alert cannot say WHICH instance (it aggregates them to keep pod identity out of the alert), so check both possibilities. If it is the PRIMARY, clients are affected and the likeliest cause is CONNECTION EXHAUSTION: every rdb-backed service opens a pool of up to 20 against the primary, and a rolling upgrade briefly doubles the pod count, so demand can exceed max_connections and application services then fail with "remaining connection slots are reserved for roles with the SUPERUSER attribute". If it is a STANDBY, clients are unaffected and this is a failing replica rather than an outage. Run `SELECT count(*) FROM pg_stat_activity` against `SHOW max_connections` as a superuser, which still works while this fires, and compare per instance.

No CloudNativePG metrics collector is being scraped

**Qué significa y qué hacer.** Nothing is reporting cnpg_collector_up in namespace ‹namespace›, so whether the PostgreSQL instances there can answer their own metrics collector is UNKNOWN rather than good — and while this fires, CNPGClusterUnusable CANNOT fire, because it reads the series this rule says are missing. ### CNPGControlPlaneUnavailable {#cnpgcontrolplaneunavailable}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-control-plane`

**Qué significa y qué hacer.** ‹deployment› in namespace ‹namespace› has zero available replicas. ## `devicechain.database-storage`

### DatabaseVolumeAlmostFull {#databasevolumealmostfull}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-storage`

A database volume is almost full

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is over 85% full. A PostgreSQL volume that fills does not slow down, it stops the database, and failing over does not rescue it: every replica holds the same data, and when the cause is unshipped WAL it is the primary that fills first. Grow it now: CloudNativePG expands a Cluster's volumes in place where the storage class supports expansion, by raising spec.storage.size (or spec.walStorage.size for a -wal claim). Reclaiming space is mostly not an alternative, because the tables that grow are append-only and stored events point at their rows. To see which tenant is behind it, on the relational primary (dc-rdb): SELECT tenant_id, count(*) FROM "device-management".geo_fence_set_versions GROUP BY tenant_id ORDER BY 2 DESC LIMIT 10; If this is a -wal claim, treat it as a stalled archiver first — unshipped WAL is retained until it ships, and the WAL archiving alerts say why it is not shipping.

### DatabaseVolumeCritical {#databasevolumecritical}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-storage`

A database volume is over 95% full

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is over 95% full. PostgreSQL stops writing when it fills, and CloudNativePG does not fail over a full disk. Grow the volume now (spec.storage.size, or spec.walStorage.size for a -wal claim; the expansion is online where the storage class supports it), or free space by lowering the event data retention. On a dc-tsdb claim, events the store cannot take are held in the message broker (EventStoreRefusingWrites) and ingest backs off, but that buffer is finite.

### DatabaseVolumeFillingFast {#databasevolumefillingfast}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.database-storage`

An event-store volume will be full within the hour at its current rate

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is more than half full and filling fast enough to run out of space within the hour. When it fills, PostgreSQL stops, and CloudNativePG does not fail over a full disk. If only the primary's volume is climbing while its replicas' are not, the cause is WAL the archiver has not shipped — see the WAL archiving and backup destination alerts, and fix the destination first. If every member is climbing together, it is data: ingest is outgrowing the volume, so grow it (spec.storage.size on the Cluster, where the storage class supports expansion) or shorten data retention.

### DatabaseVolumeFillingUp {#databasevolumefillingup}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.database-storage`

A database volume is over 75% full

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is over 75% full. Database storage on this platform does not come back on its own: several tables are append-only by design and nothing prunes them — the audit journal, device profile versions, entity group versions, dashboard versions, connector versions, geofence set versions and the geofence geometry archive. Each is kept for a reason: a stored event names the profile or fence-set version it was resolved against, and a dashboard or connector version is what a rollback returns to. Retention settings do not apply to any of them — those prune the time-series store, which is the dc-tsdb claims. Act while there is still room to work in: grow the volume, and find out what is producing versions. On the relational primary (dc-rdb), by tenant: SELECT tenant_id, count(*) FROM "device-management".geo_fence_set_versions GROUP BY tenant_id ORDER BY 2 DESC LIMIT 10; Substitute any other history table for the one named — audit_events in any schema, device_profile_versions or entity_group_versions in that one, dashboard_versions or connector_versions in theirs. It counts rows and names no other column, so it works on all of them; they do NOT share a payload column, and a query naming one would fail on most. Size per table is on the append_only_table_bytes series, which every service exports for its own tables. One tenant re-authoring in a loop is the usual answer. On a dc-tsdb claim, check the data-lifecycle retention settings instead; on a -wal claim, the WAL archiving alerts are where the cause is.

### DatabaseVolumeFillsWithinDay {#databasevolumefillswithinday}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.database-storage`

An event-store volume will be full within a day at its current rate

**Qué significa y qué hacer.** ‹persistentvolumeclaim› is on course to run out of space within 24 hours at the rate it has filled over the last two. When it fills, PostgreSQL stops and the platform can no longer store events. Events are held in the message broker meanwhile and new ingest is refused once the broker's backlog limit is reached, but a store that stays stopped for longer than the broker can hold loses data (see EventStoreRefusingWrites). Act now, with a day in hand: grow the volume (spec.storage.size on the Cluster; the volume expands online where the storage class allows it), shorten the data retention, or check that compression is acting (an uncompressed row is about 600 bytes). Size it against stored rows, which calculated metrics multiply by (1 + the formulas that apply to the profile).

## `devicechain.dead-letter`

### DeadLetterStoreLosing {#deadletterstorelosing}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.dead-letter`

the dead-letter store is losing records

**Qué significa y qué hacer.** Dead letters reached their final delivery attempt without being written to the store, so failures the platform recorded once are now recorded nowhere. The store's database is the thing to look at — the consumer rides out a blip in process and spends every delivery attempt before giving up, so this means an outage of minutes, not seconds. Look also at the consumer's backlog: what is lost here is a subset of what is late.

### DeadLetterWriteLost {#deadletterwritelost}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.dead-letter`

work is being lost with no record of it

**Qué significa y qué hacer.** A service gave up on a message AND could not record it as a dead letter, on a delivery that will not repeat — so the work is gone and nothing anywhere records what it was. This is the one failure on these paths with no evidence left behind, which is why it is separate from the giving-up alerts and fires faster than they do. There are four causes, and the pod's LOST error log line tells them apart. The write failed — the broker is unreachable, refusing, or out of storage, so look at JetStream. Or the service refused its own letter as malformed, which is a defect in that service. Or device-management could not encode the record of an inbound event that failed, so it acknowledged the event and nothing published says it failed, which is also a defect in that service. Or a dead-letter READER — the dead-letter store in user-management, or the command writeback in command-delivery — ran out of delivery attempts on a letter, which may now age out of the stream without having been stored or settled (its last attempt may have committed and lost only its acknowledgement, so this cause can overstate the loss); look at that service's database, where a stored letter settles the question, or its own logs. Note that a FULL dead-letter stream does not cause this — every stream discards oldest, so a full one silently evicts the earliest letters instead, which this alert cannot see.

### ReactPoisonDropping {#reactpoisondropping}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.dead-letter`

REACT is giving up on detection actions that keep failing

**Qué significa y qué hacer.** Derived events are hitting the redelivery cap with actions still failing — typically command-delivery or the message bus has been unavailable for several minutes. Every action of each detection was attempted on every delivery; the dead letter names each one that failed on the final attempt, by kind and idempotency key. Nothing replays them, so treat each named alarm, command or connector call as not carried out.

## `devicechain.device-management`

### DeviceCalloutLatencyHigh {#devicecalloutlatencyhigh}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.device-management`

Device connects are being decided slowly by the auth callout

**Qué significa y qué hacer.** For 10m the 99th percentile time to decide a ‹path› device connect has been above 250ms (‹value› now). **Qué significa y qué hacer.** The reader for durable ‹durable› held a message longer than the broker waits for an acknowledgement, so the broker handed it out again. stage=worker: a send was still running when that happened, so the message may have been sent twice -- look for a slow or unresponsive destination behind this service. stage=buffer: the reader dropped a message it had fetched but not yet handed to a worker, and the broker's redelivery is handled instead; nothing was sent twice, but the service is not keeping up.

### ReplayCoveredDeliveriesExhausted {#replaycovereddeliveriesexhausted}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.jetstream-delivery`

### JetStreamLeaseBucketNotReplicated {#jetstreamleasebucketnotreplicated}

The partition-lease bucket is not replicated

**Qué significa y qué hacer.** ‹stream› holds the partition-ownership leases that decide which pod may write. JetStream stream or bucket is not replicated as configured

### JetStreamReplicaPeersLagging {#jetstreamreplicapeerslagging}

A JetStream replica has not caught up

**Qué significa y qué hacer.** ‹stream› has had at least one online replica that was not caught up at any check for the last 30 minutes. Short lag under heavy load is normal and does not raise this. **Qué significa y qué hacer.** ‹pod› (‹job›) reported the replication of ‹stream› earlier and has not been able to read it for 15 minutes, although the pod is still running. ## `devicechain.sign-in`

### CredentialAttemptStoreFull {#credentialattemptstorefull}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.sign-in`

Password sign-ins are being checked without their per-account backoff

**Qué significa y qué hacer.** The credential-attempt store is full, so user-management is checking password sign-ins WITHOUT slowing down repeated failures on any address that is not already waiting out a delay -- and one that is waiting is protected only until that delay ends, at most 5 minutes. Sign-in itself still works -- refusing it would let whoever filled the store lock every user out -- but guessing is now limited only by the per-request field cap and the cost of each password check. The store fills when sign-ins are sent for a very large number of distinct email addresses inside ten minutes, which almost always means someone is spraying addresses. Find where the sign-in traffic comes from (the ingress logs, and user-management's rate-limited 'credential attempt store is full' warning) and block it upstream. The store drains on its own as entries expire, ten minutes after the flood stops. If the sign-in traffic is legitimate, raise instance.config.infrastructure.nats.kvStateMaxBytes, which sizes every state bucket.

### DeviceCredentialAttemptStoreFull {#devicecredentialattemptstorefull}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.sign-in`

MQTT password connects are being checked without their per-username backoff

**Qué significa y qué hacer.** The device credential-attempt store is full, so device-management is checking MQTT password connects WITHOUT slowing down repeated failures on any username that is not already waiting out a delay -- and one that is waiting is protected only until that delay ends, at most 30 seconds. Every connect, successful or not, holds an entry for ten minutes, so the store fills either when connects are sent for a very large number of distinct usernames (someone spraying usernames: find where the MQTT connects come from and block it upstream) or when a very large fleet reconnects all at once, for example after a broker restart. It drains on its own as entries expire, ten minutes after the wave stops. If the connect volume is legitimate, raise instance.config.infrastructure.nats.kvStateMaxBytes, which sizes every state bucket.

### MfaIdentityLocked {#mfaidentitylocked}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.sign-in`

An account's password is in use by someone failing its second factor

**Qué significa y qué hacer.** A second-factor lock armed on an account: twenty wrong authenticator codes were evaluated, each after a CORRECT password. Someone has this account's password and is guessing its code. The authenticator stays locked for at most fifteen minutes at a time (the person can still sign in with a recovery code), and a password holder can renew the lock. Find the account in the audit journal (operation mfa_locked, preceded by mfa_failed rows and mfa_challenged rows) and RESET ITS PASSWORD with setPassword: that rotates the account's session epoch, which also voids every outstanding sign-in challenge. Do not reset the second factor first -- while the password is known to someone else that would give them the account (the reset refuses without a new password for this reason). The source addresses are in the ingress logs.

### MfaVerificationFailuresSustained {#mfaverificationfailuressustained}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.sign-in`

Second-factor codes are being refused at a sustained rate

**Qué significa y qué hacer.** user-management has refused more than one second-factor code every ten seconds, on average, for fifteen minutes (wrong, replayed, or refused by a lock). Each attempt follows a correct password, so this is people typing their codes wrong in large numbers (a clock-skew problem on the nodes, or an authenticator app out of sync) or someone using passwords they obtained. Check that the nodes' clocks are synchronised (authenticator codes are accepted one 30-second step either side), then look at the audit journal for mfa_failed rows grouped by account and at the ingress logs for the source addresses. ### SsoIdpUnreachable {#ssoidpunreachable}

**Gravedad:** `warning` · **Grupo de reglas:** `devicechain.sign-in`

An identity provider cannot be reached for single sign-on

**Qué significa y qué hacer.** user-management has been failing to reach the identity provider of connection ‹connection› (its token endpoint or its signing keys) for ten minutes, so people who sign in through it are being refused. Password sign-in is unaffected. ### SsoStateStoreFull {#ssostatestorefull}

**Gravedad:** `critical` · **Grupo de reglas:** `devicechain.sign-in`

Single sign-on is refusing every sign-in because its state store is full

**Qué significa y qué hacer.** The single sign-on state store is full, so user-management is refusing to begin any sign-in through any identity provider (it fails closed rather than drop the protection that makes a replayed callback useless). ### SsoUnverifiedIdentityRefused {#ssounverifiedidentityrefused}
