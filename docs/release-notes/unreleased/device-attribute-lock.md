## en

- **Device attribute writes take a per-device lock.** Every write of a device's attributes now runs in a transaction and first takes a lock on that device: setting or deleting an attribute (including CLIENT scope, which used to be written without a transaction), restoring or copying a device configuration, importing facet values for devices, and deleting a device. Two writes to the same device are applied one after the other; writes to different devices do not wait for each other. The upgrade adds one database function and no tables. If an attribute row stays busy after five short retries, `setEntityAttribute`, `deleteEntityAttribute`, `restoreDeviceConfiguration` and `copyDeviceConfiguration` answer with the new retryable error code `ATTRIBUTE_WRITE_BUSY`, and nothing is written; retry the request. While the upgrade is rolling out, a write served by an upgraded pod can briefly yield to a write of the same attribute served by a pod that has not been upgraded yet. Three new metrics report this: `device_attribute_lock_wait_seconds`, `device_attribute_write_yields_total` and `device_attribute_write_deadlocks_total`.

## es

- **Las escrituras de atributos de dispositivo toman un bloqueo por dispositivo.** Toda escritura de los atributos de un dispositivo se ejecuta ahora en una transacción y toma primero un bloqueo sobre ese dispositivo: establecer o eliminar un atributo (incluido el ámbito CLIENT, que antes se escribía sin transacción), restaurar o copiar la configuración de un dispositivo, importar valores de facetas para dispositivos y eliminar un dispositivo. Dos escrituras sobre el mismo dispositivo se aplican una después de la otra; las escrituras sobre dispositivos distintos no se esperan entre sí. La actualización añade una función de base de datos y ninguna tabla. Si una fila de atributo sigue ocupada tras cinco reintentos breves, `setEntityAttribute`, `deleteEntityAttribute`, `restoreDeviceConfiguration` y `copyDeviceConfiguration` responden con el nuevo código de error reintentable `ATTRIBUTE_WRITE_BUSY` y no se escribe nada; repita la solicitud. Mientras la actualización se despliega, una escritura atendida por un pod actualizado puede ceder brevemente ante una escritura del mismo atributo atendida por un pod que aún no se ha actualizado. Tres métricas nuevas lo registran: `device_attribute_lock_wait_seconds`, `device_attribute_write_yields_total` y `device_attribute_write_deadlocks_total`.

## zh-CN

- **设备属性写入会获取按设备的锁。** 现在，对设备属性的每一次写入都在事务中执行，并首先获取该设备的锁：设置或删除属性（包括以前不使用事务写入的 CLIENT 作用域）、恢复或复制设备配置、为设备导入分面值，以及删除设备。对同一设备的两次写入会依次执行；对不同设备的写入不会相互等待。此次升级新增一个数据库函数，不新增任何表。如果属性行在五次短暂重试后仍处于占用状态，`setEntityAttribute`、`deleteEntityAttribute`、`restoreDeviceConfiguration` 和 `copyDeviceConfiguration` 会返回新的可重试错误代码 `ATTRIBUTE_WRITE_BUSY`，且不会写入任何内容；请重试该请求。在升级滚动进行期间，由已升级 pod 处理的写入可能会短暂让步于由尚未升级的 pod 处理的同一属性写入。三个新指标会记录这些情况：`device_attribute_lock_wait_seconds`、`device_attribute_write_yields_total` 和 `device_attribute_write_deadlocks_total`。
