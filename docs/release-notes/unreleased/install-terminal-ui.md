## en

#### A terminal UI for install and setup (opt-in) {#v1100-install-terminal-ui}

`dcctl install local --ui=tui` runs the whole cluster install in a full-screen terminal UI, and the new `dcctl setup local` (Preview) carries on from it to a first instance. Both are opt-in: without `--ui`, or with `--ui=plain`, which is also the path for screen readers, `dcctl install` prints, prompts and exits exactly as before. See [Install terminal UI](./install-terminal-ui.md).

- **Choosing it.** `--ui=tui` falls back to the plain output whenever stdin, stdout or stderr is not an interactive terminal, under CI, with `TERM=dumb`, and for `--dry-run`. `--ui=auto` chooses the terminal UI only on an interactive terminal, and never with `--yes` or `--dev`; with `--yes` or `--dev`, `--ui=tui` shows progress only and exits when the install ends. The logo splash animates for up to 1.2 seconds on a capable local terminal, and is a static mark, or a one-line header, everywhere else; `--no-splash` skips it. Every screen is readable with `NO_COLOR` and on a 16-colour or ASCII-only terminal, and it runs on the Windows console (Windows Terminal, PowerShell or `cmd`) with the console restored on exit.
- **Welcome and preflight.** The install first shows what it will do (the target, footprint, topology and image source, with "No changes have been made") and then runs the read-only preflight checks on screen. Every check reads PASS, WARN, FAIL, UNKNOWN, NOT NEEDED or NOT CHECKED as a word, and the focused check shows its fix. Recheck runs the checks again after you fix something, and the footprint can be switched between Standard and Compact, after a summary of what that changes, with every check run again for the new footprint. While any check fails, Continue is unavailable and there is no way past it; `--skip-preflight` is still the only way to skip the checks.
- **Cluster choices.** After the preflight, the install shows the target (a managed local kind cluster, which you can rename, or an existing context picked from the names in your kubeconfig), the footprint (Standard or Compact, with what Compact leaves out spelled out under it) and the topology (Single or HA), each marked with the flag that set it. Choose another context is also on the preflight screen. Advanced opens a drawer with editors for the monitoring stack, the bundled CloudNativePG operator and, on Compact, TLS, and says whether database backups run, as the plan decides it; every other flag you gave on the command line is listed there by name and carried into the install unchanged, and credentials show only as "configured (hidden)". Each change is checked the way the command line would check it, so a combination the command line refuses is refused on screen too, and the read-only checks run again for the changed plan: Continue stays unavailable until they pass.
- **An existing cluster is checked too, as advice.** With `--kube-context`, an "Existing cluster (advisory)" group follows the preflight checks: whether the API server's name resolves, whether it answers over a TLS certificate the context trusts, whether the context's credentials are accepted, whether they may create what the install creates (asked with access reviews, which change nothing), and whether this machine can reach the provider, chart and image registries the install uses. They never go through a proxy: when one is configured, for the context or in the environment (`HTTPS_PROXY` and the like), the rows it would carry read NOT CHECKED. These checks only read, follow no redirect, give up after 5 seconds to connect and 15 seconds to answer, and never block Continue: a problem reads WARN, and anything they cannot decide reads UNKNOWN or NOT CHECKED, never PASS. On Windows, a refused connection reads WARN ("refused the connection"). The registry checks follow the plan: a component the plan leaves out (monitoring under Compact or `--no-monitoring`, the CloudNativePG operator under `--no-cnpg`, cert-manager under Compact without TLS) is not checked and cannot warn, and the ingress controllers' charts follow the cluster's IngressClasses: Traefik's always, ingress-nginx's only when the cluster runs ingress-nginx and the install keeps it. The plain output, `dcctl preflight` and the install's own preflight are unchanged.
- **Credential plugins.** A context that gets its credentials from an exec plugin, as GKE, EKS and AKS contexts usually do, is checked for authentication and permissions too: the advisory checks run the plugin themselves, never interactively (no terminal, nothing on its input), for at most 10 seconds, and stop it together with everything it started when that time is up or you leave the screen. The credential it prints is used only for the context's API server, over the same read-only, redirect-free, proxy-free connection as any other credentials, never after it expires, and is never shown. A plugin whose entry says `interactiveMode: Always` is not run (NOT CHECKED), a plugin that is not installed reads WARN, and one that fails or prints no usable credential reads UNKNOWN; what the plugin prints as an error is never shown, since it can hold a token or a key. Legacy `auth-provider` entries are never run.
- **Nothing is installed without your approval.** Continue on the cluster choices opens a review of the plan as the command line would resolve it: the target and whether it is created or reused, the release and image registry, the footprint and topology, TLS, monitoring, backups, any warnings, and where the cluster's state will be kept. It also shows the equivalent non-interactive `dcctl install` command, which reproduces the same plan with `--yes`; a credential such as an alert webhook appears only as a placeholder, and the command is then marked as a template. The review opens with Back focused, and keys typed before it has settled are ignored, so a second Enter can never approve it. The install starts only when you choose Approve and install, and that approval also answers the question to create the local kind cluster, for that cluster only. Going back and changing anything makes a new plan: its checks run again and it needs a review of its own. Until you approve, Exit, Ctrl+C, an interrupt signal, or the terminal UI stopping ends the command having changed nothing.
- **Progress and the result.** The progress screen shows the install's stages with their state. The first Ctrl+C stops the install safely and the screen stays until it has stopped; a second Ctrl+C exits at once. A failed install names the stage, the cause, what may have changed, whether the cluster's lock was released, a command to inspect the cluster and the command to re-run once the cause is fixed; nothing is rolled back, and dcctl still exits 1. A successful one shows the `dcctl bootstrap … --ui=tui` command to run next.
- **Help on every screen.** `?` or F1 opens help on every screen of the install and of `dcctl setup local`, the progress screen included. Help lists exactly the keys the screen's footer shows, says what the screen does, scrolls on a small terminal, and changes nothing: it never answers a question, never pauses the install, and on a screen whose approval starts something the screen waits for the keyboard to be quiet again after help closes. Where `?` can be typed, in a name or a passphrase, F1 opens help.
- **`dcctl setup local` (Preview): a guided install, then bootstrap, with two approvals.** One terminal session prepares a cluster and creates a first instance on it. The cluster stage is the install's own screens and review; once the cluster is installed, a hand-over screen leads to the instance and root-key escrow choices and the instance's own review. Nothing of the instance runs without its own approval, and no key typed before a review has settled approves it. The escrow passphrase is asked for on screen and never shown. If you leave, or the instance fails, after the cluster stage, the cluster stays installed and setup prints the exact `dcctl bootstrap … --ui=tui` command that creates the instance on the same screens. It is guided only: without an interactive terminal it changes nothing and exits 2, and it has no `--yes`. Its exit status says what it left behind: 0 both done, 1 the cluster stage failed, 2 nothing changed, 3 the cluster installed and no instance created, 4 the cluster installed and the instance failed. `dcctl install` and `dcctl bootstrap` are unchanged. See [Install terminal UI](./install-terminal-ui.md#setup-local).

- **`dcctl bootstrap --ui=tui`: the instance in the terminal UI.** `dcctl bootstrap local <instance> --ui=tui` creates the instance in a full-screen terminal UI: the instance and root-key escrow choices, seeded from the command line; a review of the exact bootstrap with its equivalent command, which only **Approve and create the instance** starts; the bootstrap's stages as they run, with the escrow passphrase asked for on screen and never shown; then the escrow receipt, the one-time first-login password and the instance summary. Every flag the screens do not choose, and every flag they choose and leave as it was, is carried into the run exactly as given, empty values included, and an escrow path inside the instance's state directory is refused before the approval. With `--yes` or `--dev` it shows progress only. `--ui` on `dcctl bootstrap` has the same values, default (`plain`) and fallbacks as on `dcctl install`: without it, off an interactive terminal, under CI, with `TERM=dumb` and with `--dry-run`, `dcctl bootstrap` prints, prompts and exits exactly as before, and the escrow passphrase still comes from `--escrow-passphrase-file`, then `DCCTL_ESCROW_PASSPHRASE`, then a person. Inside `dcctl setup local`, the cluster welcome now says the instance follows. See [Install terminal UI](./install-terminal-ui.md#bootstrap-ui).

## es

#### Una interfaz de terminal para la instalación y la configuración (opcional) {#v1100-install-terminal-ui}

`dcctl install local --ui=tui` ejecuta toda la instalación del clúster en una interfaz de terminal a pantalla completa, y el nuevo `dcctl setup local` (Preview) continúa desde ella hasta una primera instancia. Ambas son opcionales: sin `--ui`, o con `--ui=plain`, que también es la opción para lectores de pantalla, `dcctl install` imprime, pregunta y sale exactamente igual que antes. Consulta [Interfaz de terminal de la instalación](./install-terminal-ui.md).

- **Cómo elegirla.** `--ui=tui` vuelve a la salida de texto siempre que stdin, stdout o stderr no sea un terminal interactivo, en CI, con `TERM=dumb` y con `--dry-run`. `--ui=auto` elige la interfaz de terminal solo en un terminal interactivo, y nunca con `--yes` ni `--dev`; con `--yes` o `--dev`, `--ui=tui` solo muestra el progreso y sale cuando termina la instalación. El logotipo inicial se anima durante un máximo de 1,2 segundos en un terminal local que lo admite, y en los demás casos es una marca estática o una cabecera de una línea; `--no-splash` lo omite. Todas las pantallas se leen con `NO_COLOR` y en un terminal de 16 colores o solo ASCII, y funciona en la consola de Windows (Windows Terminal, PowerShell o `cmd`), que se restaura al salir.
- **Bienvenida y comprobación previa.** La instalación muestra primero lo que hará (el destino, el tamaño, la topología y el origen de las imágenes, con "No changes have been made") y después ejecuta en pantalla las comprobaciones previas de solo lectura. Cada comprobación se lee como una palabra, PASS, WARN, FAIL, UNKNOWN, NOT NEEDED o NOT CHECKED, y la comprobación seleccionada muestra su solución. Recheck vuelve a ejecutar las comprobaciones después de corregir algo, y el tamaño puede cambiarse entre Standard y Compact, tras un resumen de lo que eso cambia, volviendo a ejecutar todas las comprobaciones para el nuevo tamaño. Mientras alguna comprobación falla, Continue no está disponible y no hay forma de saltárselo; `--skip-preflight` sigue siendo la única forma de omitir las comprobaciones.
- **Opciones del clúster.** Tras la comprobación previa, la instalación muestra el destino (un clúster kind local gestionado, al que se puede cambiar el nombre, o un contexto existente elegido entre los nombres de su kubeconfig), el tamaño (Standard o Compact, con lo que Compact deja fuera explicado debajo) y la topología (Single o HA), cada uno marcado con la opción de línea de comandos que lo estableció. Choose another context también está en la pantalla de comprobación previa. Advanced abre un panel con editores para la pila de monitorización, el operador CloudNativePG incluido y, con Compact, TLS, e indica si se harán copias de seguridad de la base de datos, tal como lo decide el plan; cualquier otra opción indicada en la línea de comandos aparece ahí por su nombre y se aplica a la instalación sin cambios, y las credenciales solo se muestran como "configured (hidden)". Cada cambio se valida igual que lo haría la línea de comandos, de modo que una combinación que la línea de comandos rechaza también se rechaza en pantalla, y las comprobaciones de solo lectura vuelven a ejecutarse para el plan modificado: Continue no está disponible hasta que pasan.
- **También se revisa un clúster existente, a modo de consejo.** Con `--kube-context`, un grupo "Existing cluster (advisory)" sigue a las comprobaciones previas: si el nombre del servidor de la API se resuelve, si responde con un certificado TLS en el que confía el contexto, si se aceptan las credenciales del contexto, si pueden crear lo que crea la instalación (preguntado con revisiones de acceso, que no cambian nada) y si esta máquina puede llegar a los registros de proveedores, charts e imágenes que usa la instalación. Nunca pasan por un proxy: cuando hay uno configurado, para el contexto o en el entorno (`HTTPS_PROXY` y similares), las filas que pasarían por él se leen como NOT CHECKED. Estas comprobaciones solo leen, no siguen redirecciones, se rinden tras 5 segundos para conectar y 15 segundos para responder, y nunca bloquean Continue: un problema se lee como WARN, y lo que no pueden decidir se lee como UNKNOWN o NOT CHECKED, nunca como PASS. En Windows, una conexión rechazada se lee como WARN ("refused the connection"). Las comprobaciones de registros siguen el plan: un componente que el plan deja fuera (la monitorización con Compact o `--no-monitoring`, el operador CloudNativePG con `--no-cnpg`, cert-manager con Compact sin TLS) no se comprueba y no puede avisar, y los charts de los controladores de ingress siguen las IngressClasses del clúster: siempre el de Traefik, y el de ingress-nginx solo cuando el clúster ejecuta ingress-nginx y la instalación lo conserva. La salida sin formato, `dcctl preflight` y la comprobación previa propia de la instalación no cambian.
- **Plugins de credenciales.** Un contexto que obtiene sus credenciales de un plugin exec, como suelen hacerlo los contextos de GKE, EKS y AKS, también se comprueba en autenticación y permisos: las comprobaciones de consejo ejecutan el plugin ellas mismas, nunca de forma interactiva (sin terminal y sin nada en su entrada), durante 10 segundos como máximo, y lo detienen junto con todo lo que haya iniciado cuando se agota ese tiempo o sales de la pantalla. La credencial que imprime solo se usa para el servidor de la API del contexto, por la misma conexión de solo lectura, sin redirecciones y sin proxy que cualquier otra credencial, nunca después de que caduque, y nunca se muestra. Un plugin cuya entrada dice `interactiveMode: Always` no se ejecuta (NOT CHECKED), un plugin que no está instalado se lee como WARN, y uno que falla o no imprime una credencial utilizable se lee como UNKNOWN; lo que el plugin imprime como error nunca se muestra, porque puede contener un token o una clave. Las entradas heredadas `auth-provider` nunca se ejecutan.
- **No se instala nada sin su aprobación.** Continue en las opciones del clúster abre una revisión del plan tal como lo resolvería la línea de comandos: el destino y si se crea o se reutiliza, la versión y el registro de imágenes, el tamaño y la topología, TLS, la monitorización, las copias de seguridad, las advertencias y dónde se guardará el estado del clúster. También muestra el comando `dcctl install` equivalente no interactivo, que reproduce el mismo plan con `--yes`; una credencial como un webhook de alertas solo aparece como un marcador, y el comando se marca entonces como plantilla. La revisión se abre con Back seleccionado, y las teclas pulsadas antes de que se haya estabilizado se ignoran, de modo que un segundo Enter nunca puede aprobarla. La instalación solo empieza cuando elige Approve and install, y esa aprobación también responde a la pregunta de crear el clúster kind local, solo para ese clúster. Volver atrás y cambiar cualquier cosa crea un plan nuevo: sus comprobaciones se ejecutan de nuevo y necesita su propia revisión. Hasta que la apruebe, Exit, Ctrl+C, una señal de interrupción o que la interfaz de terminal se detenga terminan el comando sin haber cambiado nada.
- **Progreso y resultado.** La pantalla de progreso muestra las etapas de la instalación con su estado. El primer Ctrl+C detiene la instalación de forma segura y la pantalla permanece hasta que se ha detenido; un segundo Ctrl+C sale de inmediato. Una instalación fallida indica la etapa, la causa, lo que puede haber cambiado, si se liberó el bloqueo del clúster, un comando para inspeccionar el clúster y el comando para volver a ejecutarla una vez corregida la causa; no se deshace nada, y dcctl sigue saliendo con 1. Una instalación correcta muestra el comando `dcctl bootstrap … --ui=tui` que se debe ejecutar a continuación.
- **Ayuda en todas las pantallas.** `?` o F1 abren la ayuda en todas las pantallas de la instalación y de `dcctl setup local`, incluida la de progreso. La ayuda enumera exactamente las teclas que muestra el pie de la pantalla, explica lo que hace la pantalla, se desplaza en un terminal pequeño y no cambia nada: nunca responde a una pregunta, nunca pausa la instalación y, en una pantalla cuya aprobación pone algo en marcha, la pantalla espera a que el teclado vuelva a estar en calma después de cerrar la ayuda. Donde se puede escribir `?`, en un nombre o en una frase de paso, F1 abre la ayuda.
- **`dcctl setup local` (Preview): una instalación guiada seguida del bootstrap, con dos aprobaciones.** Una sola sesión de terminal prepara un clúster y crea en él una primera instancia. La etapa del clúster son las pantallas y la revisión propias de la instalación; una vez instalado el clúster, una pantalla de traspaso lleva a las opciones de la instancia y del depósito de la clave raíz y a la revisión propia de la instancia. Nada de la instancia se ejecuta sin su propia aprobación, y ninguna tecla escrita antes de que una revisión se haya asentado la aprueba. La frase de paso del depósito se pide en pantalla y nunca se muestra. Si sales, o la instancia falla, después de la etapa del clúster, el clúster sigue instalado y setup imprime el comando `dcctl bootstrap … --ui=tui` exacto que crea la instancia en las mismas pantallas. Es solo guiado: sin un terminal interactivo no cambia nada y sale con 2, y no tiene `--yes`. Su código de salida indica lo que deja: 0 ambas cosas hechas, 1 la etapa del clúster falló, 2 no se cambió nada, 3 el clúster instalado y ninguna instancia creada, 4 el clúster instalado y la instancia falló. `dcctl install` y `dcctl bootstrap` no cambian. Consulta [Interfaz de terminal de la instalación](./install-terminal-ui.md#setup-local).

- **`dcctl bootstrap --ui=tui`: la instancia en la interfaz de terminal.** `dcctl bootstrap local <instance> --ui=tui` crea la instancia en una interfaz de terminal a pantalla completa: las opciones de la instancia y del depósito de la clave raíz, rellenadas a partir de la línea de comandos; una revisión del bootstrap exacto con su comando equivalente, que solo inicia **Aprobar y crear la instancia**; las etapas del bootstrap mientras se ejecutan, con la frase de paso del depósito pedida en pantalla y nunca mostrada; y después el comprobante del depósito, la contraseña de primer inicio de sesión de un solo uso y el resumen de la instancia. Toda opción que las pantallas no eligen, y toda opción que eligen y que se deja como estaba, se lleva a la ejecución exactamente como se dio, incluidos los valores vacíos, y una ruta de depósito dentro del directorio de estado de la instancia se rechaza antes de la aprobación. Con `--yes` o `--dev` solo muestra el progreso. `--ui` en `dcctl bootstrap` tiene los mismos valores, el mismo valor predeterminado (`plain`) y las mismas alternativas que en `dcctl install`: sin ella, fuera de un terminal interactivo, en CI, con `TERM=dumb` y con `--dry-run`, `dcctl bootstrap` imprime, pregunta y sale exactamente igual que antes, y la frase de paso del depósito sigue saliendo de `--escrow-passphrase-file`, después de `DCCTL_ESCROW_PASSPHRASE` y después de una persona. Dentro de `dcctl setup local`, la bienvenida del clúster indica ahora que después viene la instancia. Consulta [Interfaz de terminal de la instalación](./install-terminal-ui.md#bootstrap-ui).

## zh-CN

#### 安装和设置的终端界面（可选） {#v1100-install-terminal-ui}

`dcctl install local --ui=tui` 在全屏终端界面中完成整个集群安装，新增的 `dcctl setup local`（Preview）则在此基础上继续创建第一个实例。两者都是可选的：不加 `--ui`，或使用 `--ui=plain`（这也是屏幕阅读器用户应使用的方式）时，`dcctl install` 的输出、提示和退出方式与以前完全相同。参见[安装终端界面](./install-terminal-ui.md)。

- **如何选用。** 只要 stdin、stdout 或 stderr 不是交互式终端、在 CI 中、`TERM=dumb` 或使用 `--dry-run`，`--ui=tui` 都会回退到纯文本输出。`--ui=auto` 只在交互式终端上选择终端界面，并且在使用 `--yes` 或 `--dev` 时从不选择；使用 `--yes` 或 `--dev` 时，`--ui=tui` 只显示进度，安装结束后自动退出。在支持的本地终端上，开头的徽标会显示最长 1.2 秒的动画，其他情况下显示静态徽标或一行标题；`--no-splash` 可跳过它。每个屏幕在设置 `NO_COLOR` 时以及在 16 色或仅 ASCII 的终端上都可读，并且可在 Windows 控制台（Windows Terminal、PowerShell 或 `cmd`）上运行，退出时会恢复控制台。
- **欢迎和预检。** 安装会先显示将要做什么（目标、规模、拓扑和镜像来源，并注明 "No changes have been made"），然后在屏幕上运行只读的预检。每项检查都以文字显示为 PASS、WARN、FAIL、UNKNOWN、NOT NEEDED 或 NOT CHECKED，选中的检查会显示其修复方法。修复问题后可用 Recheck 重新运行检查；规模可以在 Standard 和 Compact 之间切换，切换前会说明这会改变什么，切换后会针对新规模重新运行所有检查。只要有任何检查失败，Continue 就不可用，也没有绕过的办法；`--skip-preflight` 仍然是跳过检查的唯一方式。
- **集群选项。** 预检之后，安装会显示目标（可重命名的托管本地 kind 集群，或从 kubeconfig 中的名称里选择的现有上下文）、规模（Standard 或 Compact，并在下方说明 Compact 会省略哪些内容）以及拓扑（Single 或 HA），每一项都标明是由哪个命令行参数设置的。预检屏幕上也提供 Choose another context。Advanced 会打开一个面板，其中可编辑监控组件、内置的 CloudNativePG operator，以及在 Compact 下的 TLS，并按计划的实际结果显示是否进行数据库备份；命令行中给出的其他所有参数都会按名称列在其中，并原样带入安装，凭据只显示为 "configured (hidden)"。每项更改都按命令行的方式进行校验，因此命令行会拒绝的组合在屏幕上同样会被拒绝，并且会针对更改后的计划重新运行只读检查：在检查通过之前，Continue 始终不可用。
- **也会以建议的形式检查现有集群。** 使用 `--kube-context` 时，预检之后会增加一组 "Existing cluster (advisory)"：API 服务器的名称能否解析，它是否以该上下文信任的 TLS 证书应答，该上下文的凭据是否被接受，这些凭据是否可以创建安装所创建的资源（通过不会改变任何内容的访问审查来询问），以及本机能否访问安装所用的提供程序、chart 和镜像仓库。它们从不经过代理：当上下文或环境（`HTTPS_PROXY` 等）中配置了代理时，需要经过该代理的行显示为 NOT CHECKED。这些检查只做读取，不跟随重定向，连接超过 5 秒、应答超过 15 秒即放弃，并且从不阻止 Continue：发现的问题显示为 WARN，无法判断的显示为 UNKNOWN 或 NOT CHECKED，绝不显示为 PASS。在 Windows 上，被拒绝的连接显示为 WARN（"refused the connection"）。仓库检查跟随计划：计划不包含的组件（Compact 或 `--no-monitoring` 下的监控，`--no-cnpg` 下的 CloudNativePG operator，不带 TLS 的 Compact 下的 cert-manager）不会被检查，也不会产生警告；Ingress 控制器的 chart 跟随集群的 IngressClass：始终检查 Traefik 的，仅当集群运行 ingress-nginx 且安装会保留它时才检查 ingress-nginx 的。纯文本输出、`dcctl preflight` 以及安装自身的预检均保持不变。
- **凭据插件。** 通过 exec 插件获取凭据的上下文（GKE、EKS 和 AKS 的上下文通常如此）同样会检查身份验证和权限：这些建议性检查会自行运行该插件，从不以交互方式运行（没有终端，输入为空），最长 10 秒；时间用完或您离开该屏幕时，插件及其启动的所有进程都会被一并停止。插件输出的凭据只用于该上下文的 API 服务器，使用与其他凭据相同的只读、不跟随重定向、不经过代理的连接，过期后不再使用，并且从不显示。条目中写明 `interactiveMode: Always` 的插件不会运行（NOT CHECKED），未安装的插件显示为 WARN，运行失败或没有输出可用凭据的插件显示为 UNKNOWN；插件输出的错误信息从不显示，因为其中可能包含令牌或密钥。旧式的 `auth-provider` 条目从不运行。
- **未经您的批准不会安装任何内容。** 在集群选项中选择 Continue 会打开一个计划审核页面，按命令行的解析方式展示计划：目标及其是新建还是复用、版本和镜像仓库、规模和拓扑、TLS、监控、备份、各项警告，以及集群状态的保存位置。页面还会显示等效的非交互式 `dcctl install` 命令，它使用 `--yes` 重现同一计划；告警 webhook 等凭据只以占位符显示，此时该命令会被标记为模板。审核页面打开时焦点位于 Back，页面稳定之前按下的键会被忽略，因此多按一次 Enter 永远不会批准它。只有选择 Approve and install 后安装才会开始，该批准同时会回答是否创建本地 kind 集群的问题，且仅针对该集群。返回并更改任何内容都会生成新的计划：其检查会重新运行，并需要单独审核。在您批准之前，选择 Exit、按 Ctrl+C、收到中断信号或终端界面停止，命令都会结束且不做任何更改。
- **进度和结果。** 进度屏幕显示安装的各个阶段及其状态。第一次按 Ctrl+C 会安全地停止安装，界面会一直保留到安装停止；第二次按 Ctrl+C 会立即退出。安装失败时会指出失败的阶段、原因、可能已更改的内容、集群锁是否已释放、用于检查集群的命令，以及修复原因后重新运行的命令；不会回滚任何内容，dcctl 仍以 1 退出。安装成功时会显示接下来要运行的 `dcctl bootstrap … --ui=tui` 命令。
- **每个屏幕都提供帮助。** 在安装和 `dcctl setup local` 的每个屏幕上（包括进度屏幕），按 `?` 或 F1 都会打开帮助。帮助列出的按键与屏幕底部显示的完全相同，说明该屏幕的作用，在较小的终端中可以滚动，并且不会更改任何内容：它从不回答问题，从不暂停安装；在批准后会启动操作的屏幕上，关闭帮助后该屏幕会等键盘再次安静下来。在可以输入 `?` 的地方（名称或口令中），按 F1 打开帮助。
- **`dcctl setup local`（Preview）：先引导安装，再执行 bootstrap，共两次批准。** 一次终端会话即可准备集群并在其上创建第一个实例。集群阶段就是安装自身的屏幕和审核；集群安装完成后，交接屏幕会进入实例和根密钥托管的选项以及实例自己的审核。实例的任何部分都不会在没有其自身批准的情况下运行，在审核屏幕稳定之前输入的按键也不会批准它。托管口令在屏幕上询问，从不显示。如果在集群阶段之后退出或实例创建失败，集群仍保持已安装状态，setup 会打印在同样的屏幕上创建该实例的确切 `dcctl bootstrap … --ui=tui` 命令。它只能以引导方式使用：没有交互式终端时不做任何更改并以 2 退出，也没有 `--yes`。它的退出状态说明留下了什么：0 两者均完成，1 集群阶段失败，2 未做任何更改，3 集群已安装但未创建实例，4 集群已安装但实例创建失败。`dcctl install` 和 `dcctl bootstrap` 不受影响。参见[安装终端界面](./install-terminal-ui.md#setup-local)。

- **`dcctl bootstrap --ui=tui`：在终端界面中创建实例。** `dcctl bootstrap local <instance> --ui=tui` 在全屏终端界面中创建实例：实例和根密钥托管的选项按命令行预先填写；对确切的 bootstrap 进行审核并显示其等效命令，只有**批准并创建实例**才会开始运行；运行时显示 bootstrap 的各个阶段，托管口令在屏幕上询问且从不显示；随后显示托管回执、一次性的首次登录密码和实例摘要。屏幕不选择的每个标志，以及屏幕选择但保持不变的每个标志，都会按原样（包括空值）带入运行，位于实例状态目录之内的托管路径会在批准之前被拒绝。使用 `--yes` 或 `--dev` 时只显示进度。`dcctl bootstrap` 上的 `--ui` 与 `dcctl install` 上的取值、默认值（`plain`）和回退规则相同：不加该标志、不在交互式终端中、在 CI 中、`TERM=dumb` 以及使用 `--dry-run` 时，`dcctl bootstrap` 的输出、提示和退出方式与以前完全相同，托管口令仍依次来自 `--escrow-passphrase-file`、`DCCTL_ESCROW_PASSPHRASE` 和人工输入。在 `dcctl setup local` 中，集群的欢迎屏幕现在会说明接下来是实例。参见[安装终端界面](./install-terminal-ui.md#bootstrap-ui)。
